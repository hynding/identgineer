# CMS

Identgineer's content management system is generated by [camis](https://github.com/hynding/camis)
from one neutral content model. The same model builds two targets:

| Target       | camis target                         | Output                 | Used for                 |
| ------------ | ------------------------------------ | ---------------------- | ------------------------ |
| `strapi`     | `strapi` (Strapi 5)                  | `generated/strapi`     | Local development        |
| `strapi-php` | `filament` with `apiStyle: "strapi"` | `generated/strapi-php` | Shared hosting (Laravel) |

strapi-php answers the same REST API as Strapi (`{ data }` envelope, `/api/<plural>` paths,
`/api/auth/local`), so a client written against local Strapi works unchanged against the deployed
CMS. `generated/` is git-ignored and rebuilt from the files below; never edit it.

| File                      | What it is                                                                   |
| ------------------------- | ---------------------------------------------------------------------------- |
| `camis.json`              | The content model (camis IR, version 1)                                      |
| `roles.json`              | Roles and their grants                                                       |
| `camis.config.json`       | The two targets and where each is generated                                  |
| `protected/`              | Hand-written code mirrored into both targets ([README](protected/README.md)) |
| `.env.example`            | Placeholder environment for both targets                                     |
| `tests/`                  | Vitest checks of the security properties of the files above                  |
| `scripts/camis.js`        | Runs a local camis checkout against this directory                           |
| `scripts/live-backend.js` | Generates and boots strapi-php for the identity SDK's live contract test     |

## Content model

Field names are the IR's neutral camelCase; each target maps them to its own columns.

### Site content (public read)

- **Page** — `title`, `slug` (unique, from the title), `summary`, `body` (block rich text), `seo`
  (component: `metaTitle`, `metaDescription`, `shareImage`, `noIndex`). Draft and publish: only
  published pages are served to readers. The content API serves `list` and `read` only; pages are
  written in the admin.
- **NavigationItem** — `label`, `href` (a site path or an `https://` URL), `order`, `placement`
  (`header`, `footer`, `utility`). Read-only API, like Page.

### Identity (owner only)

- **Profile** — one per user: `owner` (one-to-one to the user, unique), `displayName`, `avatar`
  (images only), `bio`, `language` (BCP 47; not `locale`, which Strapi and so camis reserve), `timezone` (IANA),
  `marketingOptIn` (default off).
- **BrandKit** — the `BrandKit` of `@identgineer/brand` ([Brand kits](#brand-kits)), with
  `owner` and `isPublic` (default off; a public kit can be read by anyone, see [Roles](#roles)).

### Tracking (owner only)

- **Property** — a tracked site or app: `owner`, `name`, `domain`, `allowedOrigins` (repeatable
  component of `https://` origins as a browser sends them: a lower-case host name with a top-level
  domain of letters, and a port only when it is not 443; so no `localhost`, IP address or IDN
  top-level domain such as `xn--p1ai`; an IDN name under an ASCII one is listed in its `xn--` form),
  `allowedEvents` (repeatable: an event `name` and the
  `propertyKeys` kept for it), `allowedQueryParams` (repeatable: the query parameter names a stored
  path keeps), `ingestKey` (public, unique, `pk_…`), `retentionDays` (1–400, default 180), `active`.
- **Event** — `property`, `owner` (copied from the property, see below), `name` (the tracking wire
  format's `[a-z][a-z0-9_]{0,63}`), `dedupeKey` (unique and private, see [Event ingestion](#event-ingestion)),
  `occurredAt`, `sessionId` (optional), `path` (optional), `referrerHost`, `properties` (JSON),
  `viewportClass` (`xs`–`xl`), `country` (two letters, optional). Read-only content API.
- **ConsentRecord** — append-only: `property`, `owner`, `subjectId`, `categories` (component:
  `necessary`, `analytics`, `marketing`, `personalisation`), `policyVersion`, `recordedAt`,
  `withdrawnAt`. A withdrawal is a new record. Read-only content API.

`User` (`builtin: "user"`) and `File` (`builtin: "file"`) are the targets' own accounts and media
library.

### Brand kits

A BrandKit row holds one brand kit of `@identgineer/brand` (`packages/brand/src/brand-kit.ts`),
field for field, so a client maps a row to the package's input and checks it with `parseBrandKit`.
`tests/brand-kit-model.test.ts` imports the package's constants and fails if an enumeration, a
length or a pattern below drifts from it.

| Field            | Kit field            | Rule in the CMS                                                                                 |
| ---------------- | -------------------- | ----------------------------------------------------------------------------------------------- |
| `brandId`        | `id`                 | Required, 2 to 32 characters, the tokens package's added theme id pattern; becomes `data-theme` |
| `name`           | `name`               | Required, at most 120 characters (see below)                                                    |
| `tagline`        | `tagline`            | At most 240 characters (see below)                                                              |
| `primaryColor`   | `colors.primary`     | Required, `#rrggbb`                                                                             |
| `secondaryColor` | `colors.secondary`   | `#rrggbb`                                                                                       |
| `neutralTint`    | `colors.neutralTint` | `#rrggbb`                                                                                       |
| `typography`     | `typography`         | Required, one of `TYPOGRAPHY_IDS`                                                               |
| `corners`        | `corners`            | Required, `sharp`, `soft` or `round`                                                            |
| `tone`           | `tone`               | Required, `calm`, `balanced` or `vivid`                                                         |
| `logo`           | `logo`               | Long text of at most 524,288 characters: the sanitised SVG                                      |
| `mark`           | `mark`               | The same                                                                                        |

What the CMS cannot check, every reader does: `parseBrandKit` refuses a reserved brand id, text
outside the package's character rules, a name over 60 or a tagline over 120 code points, and a logo
that is not exactly what `sanitiseSvgLogo` returns. The package has no default for `typography`,
`corners` or `tone`, so neither has the CMS. `brandId` is not unique: a unique id would tell any
user which ids other users had taken, and two kits with one id only collide on a page that shows
both.

`name` and `tagline` take twice the package's limits because the two targets count differently.
The package counts code points; strapi-php counts characters with `mb_strlen` (code points too),
but Strapi counts UTF-16 units, where a letter outside the Basic Multilingual Plane counts twice.
At the package's own limits, Strapi would refuse a valid name written in such letters. The looser
limit lets strapi-php keep a name up to 120 code points that the package refuses; readers then get
an error for that kit, never the kit.

The logo and mark are text fields holding the SVG exactly as `sanitiseSvgLogo` returned it, not
media fields:

- The server (PHP on shared hosting) cannot run the sanitiser, so it stores the text as untrusted
  input and never serves it as an image. It is only ever a JSON string in an API answer.
- Keeping SVG out of the media library means the CMS origin never serves a user's SVG with an
  image content type, which would be stored cross-site scripting on that origin when opened
  directly.
- Every reader checks the text again with `parseBrandKit` (or `isSanitisedSvgLogo`) and shows it
  only through `<img>` with `logoDataUrl`.

The bound is the sanitiser's output limit, `SVG_LOGO_LIMITS.inputBytes` (512 KiB in UTF-8): no
output is larger, and a string never has more code points or UTF-16 units than UTF-8 bytes, so
both targets' length checks let every sanitised logo through however they count. The column is
another matter, and only on MySQL: with a camis that sizes text columns from `maxLength`
(hynding/camis#123), the logo and mark (bounded text of 524288 characters) get a `mediumText`
column (16 MiB, which holds them even at four bytes a character). A MySQL database created before
that keeps its `TEXT` columns (65,535 bytes) until something widens them: the Content-Type
Builder's `camis:schema-sync` does, on MySQL and MariaDB only and only when it runs (`camis develop`
runs it, a plain production deploy does not), and otherwise a hand-written
`ALTER TABLE ... MODIFY ... MEDIUMTEXT NULL` (or `LONGTEXT`) does (see
[Capability gaps](#capability-gaps)).
sqlite and pgsql `text` hold it, as do Strapi's columns.

There is no `themeTokens` field. The theme is derived data the server cannot verify; clients
generate it from the kit with `generateBrandTheme`, which is deterministic.

### Data minimisation

Tracking stores the least that answers "what happened on my site", and nothing that identifies a
visitor:

- No IP address, no user agent string, no cookies, no email, no name, no precise location. There
  are no such fields, and `tests/content-model.test.ts` fails if one is added to Event or
  ConsentRecord.
- `sessionId` and `subjectId` are random tokens generated in the browser (16–64 URL-safe
  characters), not derived from anything about the visitor, and the two are never stored together.
- `path` keeps no fragment and only the query parameters the property lists in
  `allowedQueryParams` (others are where emails and tokens leak); `referrerHost` keeps the host
  only; `country` is a coarse two-letter code, optional, and never stored with a city or
  coordinates; `viewportClass` is a size bucket, not a resolution.
- `properties` is flat and bounded by the wire format (32 values, strings of at most 1024 code
  points), and keeps only the keys the property's `allowedEvents` lists for the event (enforced by
  the ingestion handler; camis cannot bound JSON).
- The visitor's `user` id that the tracking SDK may send is never stored.
- Events older than the property's `retentionDays` are deleted by the `PurgeExpiredEvents` daily
  schedule.

### Deviations from the brief

- `allowedOrigins` and consent `categories` are components rather than JSON, so each value is
  validated (`https://` origins, booleans per category).
- Event and ConsentRecord carry a denormalised `owner`. camis conditions cannot follow a relation
  (`record.property.ownerId`), so the owner of the event's property is copied onto the event when
  it is ingested, and the read grant checks `record.ownerId`.
- The logo and mark are sanitised SVG text, not images in the media library (see
  [Brand kits](#brand-kits)).
- Profile has no delete action: a profile goes with its account.

## Roles

| Role            | Content type   | Actions                        | Condition / assign                      | Why                                                               |
| --------------- | -------------- | ------------------------------ | --------------------------------------- | ----------------------------------------------------------------- |
| `public`        | Page           | read                           | —                                       | The site is public content                                        |
| `public`        | NavigationItem | read                           | —                                       | The site's menus                                                  |
| `public`        | BrandKit       | read                           | `record.isPublic == true`               | Show kits their owners made public                                |
| `authenticated` | Page           | read                           | —                                       | Signed-in callers do not inherit the public role on Strapi        |
| `authenticated` | NavigationItem | read                           | —                                       | As above                                                          |
| `authenticated` | Profile        | create, read, update           | `record.ownerId == user.id`, owner = me | Manage their own profile; no delete                               |
| `authenticated` | BrandKit       | create, read, update, delete   | `record.ownerId == user.id`, owner = me | Manage their own brand kits                                       |
| `authenticated` | Property       | create, read, update, delete   | `record.ownerId == user.id`, owner = me | Manage the sites they track                                       |
| `authenticated` | Event          | read                           | `record.ownerId == user.id`             | See analytics of their own properties; never write them           |
| `authenticated` | Property       | `PropertySummary` endpoint     | the handler checks the owner            | Figures of their own properties ([reads](#the-dashboards-reads))  |
| `authenticated` | ConsentRecord  | read                           | `record.ownerId == user.id`             | Show consent evidence for their own properties; never write it    |
| `authenticated` | File           | create                         | —                                       | Upload an avatar; no listing, editing or deleting files           |
| `super-admin`   | every type     | every action (publish on Page) | —                                       | camis' admin role, as Strapi's Super Admin; signs in to the admin |

- New registrations get `authenticated` (`defaultRole`).
- `public` holds no grant on User, Profile, Property, Event, ConsentRecord or File, and no
  endpoint. Its one conditioned grant reads brand kits marked public. Tracking reaches the CMS only
  through the ingestion endpoint, which is public by declaration in `camis.json`, not by a grant.
- A signed-in user holds brand kits under the owner grant only, and reads public kits without
  their credentials, as the public role (the brand package's store does). A read-only grant of
  public kits for `authenticated` was tried and dropped: a kit's `owner` cannot be filtered on
  (strapi-php answers `400 Invalid key owner`, as the user type is not readable), so
  `GET /api/brand-kits` would mix the caller's kits with every public kit of other users, with
  nothing in an answer to tell them apart. A kit of someone else is not found (404) for a
  signed-in user; a public one cannot be changed or deleted by anyone but its owner (403 for the
  public role). The owner grant is not widened: widening it to public kits would let anyone change
  them.
- No role but `super-admin` reads User or File, so a populate of a kit's `owner` shows nothing
  about the owner to anyone else.
- "owner = me" is the grant's `assign: { owner: "user.id" }`: the server fills the owner from the
  session on create and ignores an owner sent by the client.
- Every grant above is enforced as written on both targets: strapi-php, and Strapi's generated
  content API controllers (REST only; custom API tokens are refused there). See
  [Capability gaps](#capability-gaps).

## Event ingestion

Tracking needs a path that anyone can write to, that only writes, that is scoped to one property by
its public key, and that is limited by origin, size and rate. camis offers four ways to get there;
this project uses the last:

| Option                                                      | Why not / why                                                                                                                                                           |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A `create` grant on Event for `public`                      | Opens the generic `POST /api/events` to anyone with any `property` id, no key, origin, size or rate check, and on Strapi writing the relation needs `find` on Property. |
| An API token with `create` on Event                         | A token in a public script is public, and it cannot be scoped to one property.                                                                                          |
| A route policy on Event's `create`                          | Still the generic route and body shape; the policy can only refuse, not map a key to a property.                                                                        |
| **Public IR endpoints with hand-written handlers** (chosen) | One narrow route per job on both targets, the content API stays read-only, and the handler is the single place every check lives.                                       |

What is configuration:

- `camis.json` declares `IngestEvent` (`POST /api/ingest/events`) with `"public": true`.
  strapi-php routes it through `StrapiPublicRoute`; Strapi with `auth: false`. No role lists it and
  no grant is needed. Server-side consent records are not part of it (no `RecordConsent`
  endpoint): consent is the SDK's, in the visitor's browser.
- Its camis guards, enforced before the handler on both targets: `throttle` (120 a minute per
  client address, `CAMIS_ENDPOINT_INGEST_EVENT_THROTTLE_PER_MINUTE`), `maxBodyBytes` (65,536),
  `accepts` (`application/json`, `text/plain`) and `crossOrigin` (any origin, with the
  `Content-Type` and `X-Idg-Write-Key` headers, no credentials). The tracked sites are not listed in
  `CAMIS_CORS_ORIGIN`; the handler checks `Origin` against the property instead.
- Event and ConsentRecord set `apiActions: ["list", "read"]`, so neither target generates a create,
  update or delete route for them. Nothing but the endpoint can write tracking data through the
  API, whatever a role is granted.
- `public` has no grant on Event, ConsentRecord or Property, so nothing ingested can be read back
  anonymously, and the write key reads nothing.

What is hand-written, in `protected/` on both targets ([protected/README.md](protected/README.md)
has the files and the full rules): the handler, the `IssueIngestKey` hook, the
`DropClientIngestKey` route middleware and the `PurgeExpiredEvents` schedule (by each property's
`retentionDays`).

**The key is the server's.** A client creates a property without `ingestKey` (`POST
/api/properties`, as the dashboard will); `IssueIngestKey` gives it `pk_` and 40 secure random
characters, and the answer carries it. `DropClientIngestKey` takes `ingestKey` out of every create
and update body (and query string) on both targets before validation, so no client can choose,
change, clear or probe a key (a unique check on a client's value would tell whether that key is
taken). The model's pattern requires 32 to 61 random characters after `pk_`. The admin panel's
super-admin can still edit the field. Rotating a key is a follow-up: today an owner deletes the
property and creates another.

The handler accepts what `@identgineer/tracking` sends, both transports:

| Transport | Content type       | Write key                        |
| --------- | ------------------ | -------------------------------- |
| fetch     | `application/json` | `X-Idg-Write-Key` header         |
| beacon    | `text/plain`       | the body's `writeKey`, never URL |

| Answer                   | When                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------ |
| `202`, no body           | Accepted, also when some or all events are skipped (not allowed, too old, repeated)  |
| `400`                    | The batch breaks the wire format; the whole batch is refused                         |
| `403`                    | `Origin` is absent or not one of the property's `allowedOrigins`                     |
| `404`                    | The key is unknown or its property inactive; one identical answer for both           |
| `413`                    | The body exceeds `INGEST_MAX_BODY_BYTES` (default and most 65,536), before parsing   |
| `415`                    | Any other content type, or any `Content-Encoding` but `identity`                     |
| `429` with `Retry-After` | Per client address (camis' throttle) or per key (`INGEST_KEY_RATE_PER_MINUTE`, 3000) |
| `503`                    | The database failed; the SDK retries, and nothing identifying is logged              |

Each accepted event is one Event row: `property` and `owner` from the key's property, `dedupeKey`
the SHA-256 of the property id and event id (a repeat is skipped), `occurredAt` corrected for the
client's clock (`at + (now - sentAt)`, kept only from 25 hours back to 5 minutes ahead), the path
and referrer reduced as under [Data minimisation](#data-minimisation). `page_view` is always
accepted, without properties; any other event must be listed in the property's `allowedEvents`.
The IP address, the User-Agent, the visitor's `user` id and the write key reach neither the
database nor the logs; the address is kept only in camis' throttle counter, keyed by a hash.

Both targets' validators pass the request vectors the SDK's `parseTrackingBatch` passes
(`packages/tracking/src/testing/batch-vectors.json`), and both reduce paths and referrers to the
same `tests/fixtures/ingest-normalise-vectors.json`. `pnpm contract:live` sends the SDK's real
fetch (through the CORS preflight) and beacon to a live strapi-php backend and checks every
refusal, the key's reach and what is stored
(`packages/identity/src/live-contract/tracking-ingest.live.test.ts`).

**What CI covers, and what it does not.** `pnpm test` (the CI `verify` job) runs the Strapi
handler, middleware, hook and schedule against fakes of Strapi's services, and strapi-php's
validator and normaliser (`protected/app/Ingest`) on the shared vectors with plain PHP, which the
runner has (`tests/ingest-php-vectors.test.ts` fails on CI without PHP). `pnpm typecheck` checks the
protected TypeScript as the generated Strapi project compiles it, twice: with this repository's
TypeScript (`tsconfig.strapi.json`) and with the 5.4.5 that Strapi 5.48 pins
(`tsconfig.strapi-5.4.json`, the `typescript-strapi` dev dependency), so a construct only newer
TypeScript accepts fails here and not first in Strapi's build. Not in CI: the strapi-php PHPUnit suite
(`protected/tests/Feature/Ingest`, which needs a Laravel app) and the live tracking test, both run
by `pnpm contract:live` only, which needs a camis checkout and a scaffolded app; without
`IDENTITY_LIVE_BACKEND` the live suites are skipped, and the run's summary names them as skipped.
Local Strapi is never booted by any script here.

**Known limits.**

- The key is public, so anyone holding it can spend the property's per-key rate
  (`INGEST_KEY_RATE_PER_MINUTE`) from many addresses with a forged `Origin` (a script outside a
  browser sends any `Origin`), and the property's own visitors are then answered 429 until the
  minute passes. The per-address throttle only bounds each address. A deployment that sees this
  lowers the per-address rate or rotates the key (a follow-up).
- A batch of 500 events costs one database write per accepted event (on Strapi a read and a write
  each): 500 page views took about 3.5 seconds on local Strapi over sqlite.
- Two batches inserting the same events in opposite order can deadlock on MySQL or PostgreSQL; the
  database aborts one, which then answers 503, and the SDK sends it again.
- On local Strapi the body parser inflates a compressed body (up to its 1 MB JSON limit) before the
  handler refuses it with 415; camis' guard compares only the declared length (a camis gap). The
  parser itself refuses a coding it does not know, `IDENTITY` in capitals among them, with 415 in
  Strapi's error body under the name `Error` and without details, and logs it; strapi-php reads codings without regard to case and
  takes `IDENTITY`. Where the handler is reached, both targets read codings alike.
- Allowed origins cannot be `localhost`. To try tracking locally, serve the test page over https on
  a name under `localhost`, which Chrome and Firefox resolve to this machine (for example
  `https://shop.localhost:5173`, with a locally trusted certificate such as one from mkcert), and
  list that origin on the property.
- Invalid UTF-8 is refused (400) on strapi-php; on Strapi the body parser replaces it with U+FFFD
  before the handler sees it, so such a body is accepted with the replacement characters. A
  replacement character in decoded text cannot be told from one the client sent, so the handler
  does not guess.

**Upgrading a database.** Event gained `dedupeKey` (required, unique) and Property its two
repeatable components, so the strapi-php migrations were renumbered: the allowed origins'
migration is now `000010`, not `000008`. A database migrated before this change has stale
migration names; recreate it (nothing was ingested before this change).

## The dashboard's reads

The dashboard (`packages/components`, `docs/dashboard/`) reads through
`createCmsDashboardSource({ fetch, baseUrl })` from `@identgineer/tracking/dashboard`, given the
identity client's `authorizedFetch`, so every call is made as the signed-in user. It uses the
content API the owner grants already scope, and one endpoint for the figures:

| Call               | Request                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------- |
| `listProperties()` | `GET /api/properties?fields[0]=name&fields[1]=domain&sort[0]=id:asc`, every page up to 200 properties     |
| `listEvents(id,…)` | `GET /api/events?filters[property][documentId][$eq]=<id>`, 25 rows a page at most, sorted by time or name |
| `summary(id, r)`   | `GET /api/properties/<id>/summary?range=24h\|7d\|30d`, one call                                           |

The client never asks for or returns `ingestKey`. A filter by someone else's property finds no
events (the grant scopes the query), so when a list is empty the client asks
`GET /api/properties/<id>?fields[0]=name` and answers `not-found` when that is 404: an empty page
is never the answer for a property that is not the caller's. The error codes: 401 `unauthenticated`;
403 and 404 `not-found` for a property; a network failure, 429 and 5xx `unavailable`; a bad argument
`invalid-request` without sending; an answer that is not exactly the model's `invalid-response`.

**`GET /api/properties/:id/summary?range=24h|7d|30d`** (`PropertySummary` in `camis.json`) is not
public: only `authenticated` lists it in `roles.json`. Its handler (`protected/`, both targets):

| Answer | When                                                                                          |
| ------ | --------------------------------------------------------------------------------------------- |
| `200`  | The caller owns the property: `{ data: { propertyId, range, visitors, pageViews, events } }`  |
| `400`  | `range` is missing, repeated, an array or not one of `24h`, `7d`, `30d`                       |
| `401`  | The bearer token is invalid or expired                                                        |
| `403`  | No session (camis' role check, before the handler), or a token with no user                   |
| `404`  | The property does not exist or is not the caller's: one identical answer for both             |
| `429`  | More than 60 a minute from one address (camis' throttle)                                      |
| `503`  | The database failed; the error's class is logged, never its message, an id or an event's text |

Every answer carries `Cache-Control: no-store` (strapi-php's framework writes it as
`no-store, private`). Each figure is `{ value, previous, series }`: `events` counts every event,
`pageViews` the `page_view` events, `visitors` the distinct `sessionId`s (events without one are not
counted) over the whole range, not the sum of the buckets. `series` holds 24 hourly buckets for
`24h`, 7 or 30 daily ones for the others, in UTC, oldest first; `previous` is the same count over
the range before. The `value` of `events` and `pageViews` is the sum of its `series` (the
client refuses an answer where it is not). The range ends where the current UTC hour (for `24h`) or day ends, so the last
bucket is the one in progress. Each answer costs two grouped queries on the events of one property
(a `CASE` over the bucket edges, then `COUNT(DISTINCT …)` for visitors), with bound times and no
function of a database, so the same SQL runs on sqlite, MySQL and PostgreSQL. One part differs by
driver: MySQL's and MariaDB's default collations fold case, and session ids are base64url, where
`aB` and `Ab` are two sessions, so there the distinct counts compare `CAST(session_id AS BINARY)`;
sqlite and PostgreSQL compare bytes already and are sent the plain column.

Both targets are held to the same `tests/fixtures/property-summary-vectors.json`: the Strapi
handler in Vitest over `node:sqlite` with Strapi's tables (`tests/summary-*.test.ts`), strapi-php's
queries with plain PHP and PDO sqlite (`tests/summary-php-vectors.test.ts`, so `pnpm test` and CI
need PHP's `pdo_sqlite`), and the strapi-php handler by PHPUnit in the live app
(`protected/tests/Feature/Summary`, run by `pnpm contract:live`). `pnpm contract:live` also runs
the client against strapi-php with two users and events sent by the real tracker
(`packages/identity/src/live-contract/dashboard-source.live.test.ts`).

`Event.dedupeKey` is `private`: no answer carries it and a filter, sort or field list naming it is
refused with 400, on both targets; ingestion still writes and checks it.

**Known limits.**

- On the hour (or at midnight) the current range has just begun its last bucket, so it covers up
  to one bucket less time than `previous` until that bucket ends.
- Visitors are sessions, so one person in two tabs or after the session timeout counts twice.
- Events have no index on `(property, occurredAt)` (camis generates none), so a summary scans a
  property's events; retention bounds how many there are.
- `listProperties` stops after 200 properties; the rest are not shown.
- `populate=property` on `GET /api/events` shows the caller's own property in full, its
  `ingestKey` included, which is the caller's to see; never anyone else's.
- An event keeps the `owner` it was stored with. A property moved to another owner (only the admin
  panel can do that) leaves its earlier events readable by the earlier owner and out of the new
  owner's lists, while the summary counts them for the new owner.
- The SQL was run on sqlite, MariaDB 10.11 and PostgreSQL 16 (strapi-php's, with native and emulated
  prepares), and Strapi's on sqlite through Strapi 5.48 itself, once, by hand. Strapi's MySQL form
  was run on MariaDB 10.11 through PDO, on tables shaped as Strapi's, with every vector (sessions
  differing only by case among them), but not through knex and `mysql2`, which are not installed
  here; Vitest checks the SQL Strapi's `mysql` client is sent. Strapi's on PostgreSQL, and MySQL 8
  itself, were not run.

## Commands

camis is not published to npm. Clone it beside this repository and point `CAMIS_DIR` at it:

```sh
git clone https://github.com/hynding/camis ../camis && pnpm -C ../camis install
export CAMIS_DIR=../camis

pnpm cms:validate   # check camis.json against the IR schema
pnpm cms:generate   # dry run: list each target's files and capability gaps; writes nothing
pnpm cms:build      # write both targets into cms/generated/
```

`pnpm test` checks the files without camis.

### Deployment settings for sign-in

The strapi-php section of [`.env.example`](.env.example) lists every setting the identity SDK
(`packages/identity`) needs to work safely, each with a one-line reason: refresh sessions
(`CAMIS_JWT_MANAGEMENT=refresh`) and their lifespans, the refresh cookie (`Secure`,
`SameSite=Strict`, `Path=/api/auth`), CORS (the site's origin, never `*`; the SDK's headers;
`Retry-After` exposed), the throttles, account email with account existence hidden (registration
and the confirmation resend answer every address alike), the per-recipient mail bound and a cache
store that counts them atomically. `tests/deployment-env.test.ts` fails if
one goes missing or changes away from what the SDK needs (confirmation on, positive throttles,
ordered session lifespans, https links to the site, placeholders for every secret), if a setting
lacks its reason, or if the live contract's server runs with other values for the SDK's settings.

### Live contract test

`pnpm contract:live` (from the repository root) runs the identity SDK, and the brand kit store of
`packages/brand` through it, against a real strapi-php backend generated from this directory. It
needs `CAMIS_DIR` and PHP 8.3 or newer with the extensions Laravel and Filament need (it names the PHP it found when older); the first run also
needs Composer, as it scaffolds the Laravel app with `camis scaffold filament`, which downloads
packages from Packagist. `scripts/live-backend.js` then, on every run:

1. writes `generated/live/camis.config.json` (the filament target only, into
   `generated/live/strapi-php`) and runs `camis build` with it;
2. writes the app's `.env` with a fresh `APP_KEY` and salts and the SDK's settings from
   `.env.example`, with sqlite, mail to the `log` driver and `APP_ENV=production`; PHP gets only
   the shell's path, home, temp, locale, Composer, proxy and CA variables plus these settings, so
   nothing exported in the shell changes the backend under test;
3. runs the ingestion and summary handlers' PHPUnit tests (`protected/tests/Feature/Ingest` and
   `protected/tests/Feature/Summary`) in the app, with the shared vector files, and stops if they
   fail;
4. migrates and seeds a fresh sqlite database for each of six servers that differ only in email
   confirmation, hidden account existence, throttle rates and access token lifespan (`main`: off,
   relaxed; `confirmation`: on, relaxed; `disclosing`: on, relaxed, accounts shown as Strapi
   answers, so the SDK is checked against both; `throttled`: off, 3 a minute for every credential
   group, refresh included; `shortLived`: off, relaxed, access tokens living 2 seconds;
   `ingestLimited`: off, relaxed, but ingestion limited to 6 a minute per address and 3 per key;
   all but `disclosing` hide accounts), and serves each with PHP's built-in server on a free
   port of 127.0.0.1 only, logging to `generated/live/<server>.server.log`;
5. writes `generated/live/backend.json` describing them, runs the command after `--` with
   `IDENTITY_LIVE_BACKEND` set to its path, and stops the servers.

A server that exits stops the run at once, with the end of its log. SIGINT, SIGTERM and SIGHUP are
passed on to the command; the script waits for it, stops the servers and exits with 128 plus the
signal's number. `IDENTITY_LIVE_DIR` puts everything under another directory (the script's own
tests use it).

Without a command (`CAMIS_DIR=../camis node cms/scripts/live-backend.js`) it serves until
interrupted, so the suite can be run repeatedly with
`IDENTITY_LIVE_BACKEND=cms/generated/live/backend.json pnpm vitest run --project identity-live`.
Each boot starts with fresh databases, throttle buckets and mail bounds; servers kept up keep them
between runs, so a rerun within a minute may wait out the throttled server's register window.

The app scaffolded before camis added the middleware-priority line to `bootstrap/app.php`
(`prependToPriorityList(ThrottleRequests, StrapiJsonBody)`, generated DEPLOY.md) does not have it,
and the live run does not add it: the users-permissions routes count with camis' own throttle, not
Laravel's `ThrottleRequests`, so the line changes nothing they do. A fresh scaffold has it. Such an app
also lacks the `CamisAuthServiceProvider` line in `bootstrap/providers.php` (the admin panel's
sign-in, nothing the SDK uses); the live script adds that documented line after the panel's entry
when it is missing, so the app matches a fresh scaffold and the build no longer warns. It also
lacks camis' line that leaves the endpoint's CORS to camis (`ENDPOINT_CORS_SKIP` in
`bootstrap/app.php`, generated DEPLOY.md): without it Laravel's own CORS answers the ingestion
preflight without `X-Idg-Write-Key`, and the SDK's fetch is blocked. The live script adds those
lines after the `StrapiErrors` block when they are missing.
Everything it writes is under the git-ignored `generated/live`, one scaffold only; delete that
directory to scaffold again. A scaffold counts as done only once `generated/live/strapi-php.scaffolded`
is written, after it has finished, so one interrupted is started again from nothing. After
scaffolding it removes the VCS checkouts Composer leaves in
`vendor` when it clones packages rather than downloading their archives, which can take
gigabytes. It is not part of `pnpm test` or CI, which have no camis checkout.

Running the generated projects needs each target's own tooling, which this repository does not
install:

- **Strapi**: `cd cms/generated/strapi`, copy the Strapi section of `.env.example` to `.env`, then
  `npm install && npm run develop`.
- **strapi-php**: `camis scaffold filament cms/generated/strapi-php` once (needs PHP and
  Composer), then `pnpm cms:build`, copy the strapi-php section of `.env.example` to `.env`, and
  follow `cms/generated/strapi-php/DEPLOY.md` (`php artisan migrate`,
  `php artisan db:seed --class=RolePermissionSeeder`, `php artisan camis:admin <email>`). The
  `PurgeExpiredEvents` schedule needs cron to run `php artisan schedule:run` every minute.

`camis develop` (editing the model in the admin's Content-Type Builder) works against strapi-php;
commit the `camis.json` and `roles.json` it writes.

## Capability gaps

`pnpm cms:generate` reports these today (camis `master`, Phases 94 and 95). Each is a camis
limitation, not a choice made here.

**What Strapi enforces now.** camis' generated Strapi project enforces grant conditions and
`assign` on the content API, so ownership is enforced on local Strapi as on strapi-php (generated
controllers, scoped queries, relation-write checks, write body validation and the upload API;
details in camis' `packages/cli/README.md` and `docs/PLAN.md`, Phases 94 and 95):

- `find` is narrowed to the caller's own rows in the query; `findOne`, `update` and `delete` answer
  404 for a row the caller cannot read and 403 for one it can read but not change.
- `create` evaluates the grant's condition on the fields sent, and `assign` sets the owner from the
  session, replacing an owner sent on create and dropping one sent on an update.
- A populate or filter that reaches Profile, BrandKit, Property, Event or ConsentRecord carries
  the same scope; a write that links a row the caller cannot read is 403.
- A write body with an unknown key, a malformed relation or media item, or a non-object `data` is 400. Populating a file's `related` entries (a polymorphic relation) is refused with 400.
- The upload API attaches only to an entry the caller may update, and records the uploader.

Limits that remain on Strapi, for this model:

- **REST only.** GraphQL, if added by hand, and a `protected/` file that replaces a generated
  controller are not enforced.
- **Custom API tokens are refused (403) on enforced routes.** Only full-access and read-only
  tokens work there, and they are not narrowed by row conditions; keep them off any client.
- **The media library is not scoped by uploader.** `GET /api/upload/files` and `/files/:id` answer
  as Strapi's plugin does, so a role that may read files lists every file. In this model only `super-admin` reads files;
  `authenticated` may only upload.
- On MySQL a string comparison in a list filter follows the column's collation, so a filter may
  let through rows the condition would deny; entry checks are exact. This model's conditions
  compare numeric ids, so it is not affected today (unverified for future string conditions).
- Deleting an entry drops its links without asking for update on the entries at their other ends.
- **How far this is verified.** camis tests the controllers against a fake of Strapi and the
  scoped queries on Strapi's query engine over sqlite; its live boot job runs Strapi on sqlite
  only and does not cover drafts, nested populates, MySQL or Postgres.
- **A database created before this camis version** keeps the `users-permissions.user.find` that
  camis used to grant the `authenticated` role, which lets every signed-in user list usernames
  and emails at `GET /api/users`. Recreate the local database, or remove that permission from the
  Authenticated role by hand.
- **A database created before `Profile.locale` became `language`** has a `locale` column and no
  `language` one, on both targets. Recreate the database, or rename the column by hand before the
  first run: `ALTER TABLE profiles RENAME COLUMN locale TO language` (SQLite, MySQL 8 and
  PostgreSQL). Left alone, schema sync does not rename it: as camis documents it (Strapi's own sync,
  and `camis:schema-sync` of strapi-php), it adds the missing `language` column empty and drops the
  `locale` column the model no longer declares, so every stored locale is lost. Local Strapi was not booted to confirm
  this.

**Reported by `pnpm cms:generate`.**

- `conditionContext @ <type>.authenticated` (Profile, BrandKit, Property, Event, ConsentRecord)
  and `@ BrandKit.public`: the admin-panel copy of the role cannot read `record.ownerId` or
  `record.isPublic`, so in the admin panel its condition denies every entry; the content API
  enforces it. Use the `super-admin` role in the admin.
- `userRelationWrite @ <type>.super-admin` (the same five types): to let the role write a relation
  to the user, camis also grants it `users-permissions.user.find`. That adds nothing here:
  `super-admin` already holds every action on users. The `authenticated` role is not reported and
  gets no `user.find`.
- `draftPublish @ Page.slug` (strapi-php): a draft and its published version share the slug, so the
  database does not enforce its uniqueness.
- `remoteDataTransfer` (strapi-php): `strapi transfer` needs a WebSocket server; move data as an
  archive instead (see `DEPLOY.md`).
- `endpointBodyLimit @ Event.IngestEvent` (Strapi): `strapi::body` refuses a `text/plain` body over
  57,344 bytes (its default text limit) with 413 before the endpoint's 65,536-byte cap applies, so
  on local Strapi a beacon between the two sizes is refused. The SDK's `maxPayloadBytes` default
  (32,768) is below both.

**Found while storing brand kits, fixed in camis.** Both need a camis that includes the fixes.

- An update that sets an optional field to `null` clears it on strapi-php, as on Strapi, so an
  update can clear a brand kit's `tagline`, `secondaryColor`, `neutralTint`, `logo` or `mark`
  ([hynding/camis#122](https://github.com/hynding/camis/issues/122)). An older camis kept the old
  value. The brand kit store still rejects a write the CMS answers with other values than were sent
  as `not-applied`, as a safeguard against a server that does not apply it, and
  `packages/identity/src/live-contract/brand-kit-store.live.test.ts` checks the clearing against
  the real backend.
- A `text` field's column is sized from its `maxLength` (`text`, `mediumText` or `longText`)
  ([hynding/camis#123](https://github.com/hynding/camis/issues/123)), so the brand kit's `logo` and
  `mark` (524288 characters) are `mediumText` on MySQL. A MySQL database created before the fix keeps
  its `TEXT` columns (65,535 bytes), as a migration that has run is not run again. The Content-Type
  Builder's `camis:schema-sync` widens such a column when the model declares a larger one, on MySQL
  and MariaDB only and only when that sync runs (`camis develop` runs it, a plain production deploy
  has no such step). Otherwise run `ALTER TABLE ... MODIFY ... MEDIUMTEXT NULL` (or `LONGTEXT`) by
  hand (camis's CLI README, "Text columns"). Until then a logo or mark over 64 KiB cannot be stored
  whole there. sqlite and pgsql have one text type. The
  column type is not the server's or the request's limit (MySQL's `max_allowed_packet`).

**Not reported by camis but limiting this model.** Conditions cannot follow a relation (hence the
denormalised `owner` on Event and ConsentRecord); an endpoint's guards cannot check `Origin`
against a row or limit per key (hence the handler's own checks); the Strapi target generates no
unique index, so `Event.dedupeKey` is unique only by the handler's per-process lock there (two
Strapi processes could both store a repeat; strapi-php has the index); no read route has a throttle either, so
public brand kits, which anyone may list page by page by design, can be enumerated as fast as the
server answers (pages are capped at 25 rows, `CAMIS_REST_MAX_LIMIT` for strapi-php and
`protected/config/api.ts` for Strapi, whose generated `maxLimit` reads no variable; a list asks for
summaries without logos); JSON fields cannot be bounded; media
fields cannot name MIME types (strapi-php's global `CAMIS_UPLOAD_ALLOWED_TYPES` is used instead,
without SVG; brand logos are text for that reason among others); string lengths are counted as
each target counts them (UTF-16 units on Strapi, code points on strapi-php), hence the doubled
brand kit name and tagline limits; a field cannot be unique per owner; relations have no delete
behaviour, so on strapi-php a property with events cannot be deleted until its events are purged;
there is no read-only field (so `ingestKey` is kept server-owned by a route middleware, which the
admin panel does not pass through); and one
`protected/` directory is mirrored into both targets.

**Deployment recommendation (Feature 14).** Put a rate limit per client address on
`GET /api/brand-kits` (and `GET /api/brand-kits/:id`) in the reverse proxy or the host's web server
config, since neither target throttles reads.

**Public brand kits.** A `public` read grant on BrandKit conditioned on `record.isPublic == true`
is within what camis enforces on both targets (a read condition of `eq` over `record.<field>`
against a literal, with the public role as the caller without a session), and the model has it. A
signed-in user does not inherit the public role on Strapi, and the separate read-only grant for
`authenticated` that would cover it is left out for the reason given under [Roles](#roles). Both
targets combine a role's grants on one type with "or" (strapi-php's policy and list scope test each
condition of the role; Strapi's generated controllers hold each action under every condition that
grants it), so such a grant would add public kits to every signed-in list, not replace the owner's.
